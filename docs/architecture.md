# Architecture

This guide grew one increment at a time, so later sections refine earlier ones. The first four sections state the contracts everything else follows. After them:

- **Interface**: Workbench shell · Console projects · Shape checks · Links, commands, and comparison
- **Recording**: Variable names from source spans · Recorded module stages · Forward call configuration · Source snapshots, Git, and environments
- **Explaining operations**: Relation rules · More cell rules · Whole-tensor motion · Failure diagnosis · and one section per dedicated view (patch embedding, layout replay, linear projection, joins, convolution, pooling, layer normalization, shifted windows)
- **Inputs, weights, and models**: Reusable generated inputs · Uploaded tensor inputs · Sample inputs and pixel views · Immutable model checkpoints · Model composition · Custom component library · Explicit builder dependencies

## Trace first, presentation second

```text
Project draft → worker → real PyTorch execution
                           ↓
                       trace recorder
                           ↓
                  operation adapter registry
                           ↓
                  immutable versioned run
                           ↓
                 frontend presenter registry
                           ↓
                 reusable tensor renderers
```

Every run, analysis and watch runs in a fresh worker process, so user code never shares a process with the server or with another job. Importing PyTorch takes most of a second, longer than many runs, so the server keeps one worker of each kind (`tensorviewer.worker`, `tensorviewer.evaluate`) started ahead and waiting with its libraries imported (`standby.py`). A job hands the waiting worker its folder and arguments over standard input; the worker runs that one job and exits, and the server starts the next. A project with its own Python environment starts its worker cold, as before. Once its answer is written, a worker leaves with `os._exit(0)`: tearing down PyTorch and the interpreter for a process that ends anyway cost about 0.1 s a job. A run of the GPT example went from about 1.0 s to about 0.16 s, and a watch expression answers in about 0.05 s. The analyses that run the model many times (the logit lens once per layer, a causal trace once per layer and word, a knockout sweep once per slice, step timings six times) record those passes with `Recorder(values=False)`: they read only the steps and their shapes, so a pass skips copying, summarizing and saving each tensor's values, and it skips watching live tensors for changes in place, which no analysis of those passes reads. A full run still reads each live tensor's state once before a call, for both the check for changes made outside a recorded call and the before-and-after comparison. A worker reads the installed package versions it reports while it waits, not after it gets a job. A step's time covers only its own call, so timing passes lose nothing by skipping values. A run records its steps without `torch.device("cpu")` around it: the CPU is where new tensors land anyway, and as a context it routed every tensor call, the recorder's reads of each live tensor included, through a Python dispatch. Only a shapes-only run, whose tensors must land on the meta device, still sets one. That made a GPT run about 114 ms through the API instead of 178 ms, the image captioner's 184 ms instead of 335 ms, and every analysis pass a little faster, and step timings no longer include that dispatch. On the GPT example a causal trace went from about 4.3 s to about 0.6 s, its logit lens from about 0.2 s to about 0.1 s, its step timings from about 0.5 s to about 0.16 s, and a 16-slice sweep from about 1.35 s to about 0.3 s.

A trace has ordered operations plus tensor references. The ordered list powers playback; references build the journey graph. The frontend links each operand to its latest recorded producer, lays out dependency levels from left to right, and separates parallel branches vertically. Multiple operand positions and multiple outputs are retained. Unproduced parameter roots remain available through operation tensor details, while external captured tensors appear as explicit roots. Selecting a node highlights its recorded ancestors and source line; selecting an executable source line locates its operation. The graph is a view of one saved execution, not a graph editor or a symbolic model of every possible path.

Selecting a node also opens `TransformationFocus`, an unscaled panel over the canvas that reuses `OperationView` and `TensorCard` for the incoming tensors, operation, and output. `JourneyInspector` is a code-only Executed code sidebar; it no longer creates an independent copy of the tensor lesson. Specialized lessons retain their Tensor details fallbacks in the central view. Container queries keep diagrams side by side when space allows and stack them on narrow screens. Dismissing focus restores the prior overview pan and zoom without losing the selected node.

The shared tensor explorer separates the viewing plane from logical coordinates. Users can choose any two axes, navigate remaining axes as slices, and inspect recorded values without executing a tensor operation. Each tensor has a local cursor; presenter-provided highlights indicate supported relationships. A selected cell drives its slice and page, so keyboard navigation and mapped selections stay visible. Storage positions use the recorded offset plus the coordinate/stride dot product, and are labeled with their storage ID. Scalars have one selectable cell; any zero-sized axis means there are no cells to draw.

Rendering is bounded to an 8 × 8 window (optionally 16 × 16) per explorer. Visible-element counts and row/column ranges distinguish that window from the whole tensor. `TensorNavigation` uses constant-size numeric controls instead of one option per slice. Coordinate entry validates the original axis order, selects the exact logical element, and brings it into view. Cell labels use compact rounding while the selection readout retains the full recorded value. Shared display preferences keep the central lesson and its related tensor views consistent.

Every captured tensor state has its own ID. Actual storage identity is recorded separately. Values are serialized at capture time, so a later in-place operation cannot rewrite history. `Operation.mutations` records before/after pairs as `write`, `alias`, or `metadata`, separately from actual return values. Version counters, storage identity, shape, strides, offset, and dtype are observed around intercepted calls. Known layout-only operations do not cause value updates to other aliases merely because their shared version counter increments.

A storage write immediately snapshots every already-captured tensor on that storage, including aliases with independent version counters. These are storage-level dependencies: disjoint slices may have unchanged values. Snapshotting is eager to preserve intermediate writes accurately; all additional states count toward the existing capture budget. Large snapshots stay paged, and Shapes-only mode retains metadata without values. No element-level write mask or synthetic PyTorch operation is invented.

`producedTensorIds` resolves explicit returns and mutation states. The graph links prior alias states into the writer with dashed storage edges and links their refreshed states to later consumers. Stage folding retains effects that cross a module boundary even if the module did not return them. `MutationView` compares one selected before/after pair using the existing bounded tensor explorer and 3D dialog. Original operands and return values remain separately inspectable.

This remains an eager `TorchFunctionMode` recorder. Native storage operations that bypass that boundary (including `set_` in the supported environment) cannot always be attributed. If a previously captured tensor changes outside an intercepted operation, a tracking notice accompanies the new captured root. External NumPy/raw-storage writes that do not change observable tensor metadata/version counters cannot be detected. Old traces default to empty mutation lists; rerun them to obtain the new provenance.

The recorder runs at the high-level `TorchFunctionMode` boundary to retain readable names such as `reshape`, `contiguous`, and `linear`. It also captures generic tensor-returning calls. This is eager execution, not a compiler or a replacement implementation of PyTorch. Fused operations are shown as a single call.

## Semantic units

An operation adapter supplies an explanation and supported interaction capability. Layout adapters can provide an exact output-to-input index map. Matrix multiplication instead supplies a contribution interaction: the frontend selects the row and column from recorded operands. The trace retains PyTorch's result; displayed arithmetic is rounded for readability.

Capabilities are deliberately separate from operation names. Several operations can reuse the same mapping presenter or tensor renderer without sharing an incorrect explanation. Unknown operations remain inspectable. Semantic axis labels come from explicit annotations or transformations that preserve known meanings. A `# axes:` annotation names the operation that produces the statement's value (`Recorder.assignment` reports it as exact), plus `return` lines and lines without column positions. `Recorder.backfill_axes` then walks back through that statement's intermediates while each step keeps axes (`SAME_AXES`, same shape) or permutes them (`lesson.axis_order`, inverted). Other intermediates keep their propagated or `axis N` names. Without an annotation, `feature_axes` names `linear` outputs after their input (only the last axis changes size) and `embedding` outputs as the indices' axes plus `features`, so names declared on `# input` lines reach attention blocks; `gather` and `index_select` keep their source's names. Readable default names (`x[:, 0]`, `~mask`) are kept as templates and rebuilt by `final_default_names` once every operand's name is settled, because an operand on an assignment line is provisionally called by the assigned variable.

## Keep execution and teaching honest

- Preserve actual source locations and original inputs, including parameter tensors.
- Treat memory copying independently from logical rearrangement.
- Never invent an element-to-element path through a computation.
- Do not infer an image grid, token meaning, or head axis merely from dimension sizes.
- Label partial executions and keep successful steps when later operations fail.
- Store the exact source and input specification with every run.

## Completed roadmap increments

The current milestone includes shifted-window/relative-bias lessons, branch/join authoring, multi-file entry points, committed Git source import, and explicit dependency environments. These build on the existing hierarchical model, trace recorder, immutable runs, and bounded tensor renderers. The scoped limits below remain intentional; Git import is a source snapshot importer rather than an arbitrary repository installer.

Large value snapshots are written as immutable NumPy arrays by the worker before later mutation can change their contents. Small tensors remain inline for backwards compatibility. `TensorState.value_source` distinguishes inline values, paged values, and shape-only metadata. The run response excludes large arrays; the bounded values endpoint reads at most 256 logical positions using a memory map. The client cancels stale window requests and shows loading/error states rather than stale values.

Layout adapters emit compact `mapping_rule` descriptors for large tensors. Identity, permutation, and unfolding relationships are evaluated per coordinate, avoiding an array with one entry per element. Large inverse unfold memberships are capped at 256 highlights. Dot-product and normalization views also bound the highlighted contributors and do not claim numerical calculations from missing data.

The recorder supports 8,388,608 elements per value tensor and 32 million across captured states. Shapes mode constructs the module and inputs on PyTorch's meta device and records no numeric values, allowing up to 2^40 logical elements per tensor. Value-dependent code and unsupported meta kernels report failures explicitly. Neither mode removes the 20-second worker or 256-operation bounds. Hosted untrusted execution still needs a separate security boundary; the current local worker is not that boundary.

## Patch embedding lesson

`operations/spatial.py` qualifies complete Conv2D patch tilings using recorded kernel size, stride, padding, dilation, groups, and output shape. The lesson reports `patch_projection` and a rectangular `patch_size`. General or incomplete convolutions keep a generic inspector. The shared PatchEmbedding source records projection, flatten, and transpose as distinct real operations in both examples and composed models.

`patches.ts` links those steps through captured tensor IDs and validated identity/permutation rules, rather than matching shapes alone. Its pure helpers map patch positions, input pixels, kernel entries, projected features, and token coordinates. `PatchEmbeddingView` uses those mappings and the existing paged-value hook to display a synchronized spatial grid, selected input channel, projection kernel, one contribution, and the recorded output. Pixel windows are explicitly views, not synthetic execution nodes. The first lesson supports at most 8 × 8 visible patches/pixels and eight visible output features, independent of batch, image, kernel, or embedding size. Shape-only runs use the same coordinate interactions without values.

Tests compare captured results to PyTorch, verify exact rectangular patch contributions, reject unsupported convolution variants, follow real dependencies, and bound large shape-only traces and frontend windows.

## Selected-element layout replay

`layoutTransition.ts` validates nonempty, value-preserving bijections from the recorded layout capability, axis order, shapes, dtype, and selected output-to-input mapping. It uses logical flat indices for reshape and coordinate permutation for axis reordering. Storage positions are calculated independently from offsets and strides. Compatible older explicit maps are supported; one-to-many windows, dtype views, failed operations, and unverified layouts do not get this animation.

`LayoutTransitionView` animates one selected marker through source, mapping-rule, and destination stops. Both endpoints use bounded 4 × 8 last-two-axis windows with labeled fixed leading coordinates. The pure scene and interpolation helpers place stops exactly at the selected cells. Numeric values come from immutable snapshots through the existing paged hook; shape-only runs show a marker without fabricated values. Animation never executes model code or adds synthetic operation nodes.

Playback uses a cancellable animation frame, pauses when the document is hidden, and resets on selection changes. Manual steps and scrubbing remain available with reduced motion. The focused view adapts to a vertical diagram on narrow screens. Tensor details stay mounted to preserve viewing axes and selection. Tests cover reshape, permutation, noncontiguous copies, scalar/unit axes, legacy maps, rejected variants, billion-element windows, and exact playback stops.

## Linear projection lesson

The compute adapter marks standard, nonempty `linear` calls as `linear_projection` after validating input, matrix-weight, optional vector-bias, and output shapes. `linear.ts` validates those same recorded operands, including compatible older runs, and provides pure coordinate mappings. Selecting an output fixes its leading coordinates and output feature; selecting an input changes the input vector and contribution index; selecting a weight changes the output feature and contribution index. Weight rows are output features, and columns are input features. Noncontiguous storage does not change logical snapshot indexing.

`LinearProjectionView` reuses `TensorCard`, its 3D explorer, direct-index controls, and `useTensorValues`. It allocates an eight-term contribution window independently of tensor size. Complete sums fetch at most 256 input/weight pairs; larger dimensions display only the selected window sum. Missing, non-finite, and overflowing products never become fabricated finite results. Bias and actual output come from the immutable run. Browser arithmetic is explicitly approximate because floating-point accumulation may differ from PyTorch. Shape-only traces use the same mappings without numbers. The Tensor details fallback preserves the lesson selection when switching back.

Backend checks compare selected contributions and complete outputs with PyTorch across input ranks, optional bias, keyword operands, noncontiguous views, paged snapshots, and meta tensors. Frontend tests cover row orientation, leading-coordinate preservation, input/weight selection, bounded final windows, and unavailable numeric data. Manual acceptance checks cover keyboard selection, 3D selection, narrow screens, and numeric paging.

## Recorded module stages

`Trace.module_calls` is an additive, optional-on-old-runs collection of actual `nn.Module` invocations. Forward hooks record a unique call ID, parent call, canonical module path, class, operation interval (exclusive end), and entry/return tensor IDs. Snapshot work in hooks temporarily suspends operation recording, so metadata capture does not invent detach or reshape steps. Repeated invocations stay separate. Calls with no recorded tensor operations are discarded; failed calls still retain their executed interval and do not receive synthetic outputs.

`stages.ts` selects calls spanning at least two operations. Generated composition wrappers are omitted while real component and nested-module calls remain available. `collapseJourney` contracts selected call intervals on the original dependency graph, retains crossing tensor edges, and lays out the resulting DAG. It never rewrites the trace or infers a stage from equal tensor shapes. The `Stages` navigator expands calls one level at a time, while `All operations` restores the full graph. `StageFocus` reuses bounded `TensorCard` inspectors for actual call inputs and outputs and links to all enclosed operations. Direct operation navigation opens its ancestor groups. Reveal mode keeps all stages expanded, and the minimap follows the same visibility cutoff as the canvas.

This initial grouping follows module calls, not arbitrary Python regions. Functional operations between modules remain individual nodes. Older executions remain ungrouped until rerun. Recorded storage dependencies survive folding; boundaries still distinguish actual module returns from side effects. Unintercepted external writes retain the recorder limitations described above.

## Reusable generated inputs

`InputFixtureDraft` validates a named `InputSpec` and recording mode. The `input_fixtures` SQLite table stores immutable configuration snapshots through GET/POST `/api/v1/input-fixtures`. Saving and listing never execute model code or allocate tensors; shape-only entries retain the full logical shape within the existing 2^40 limit. Value entries use the same 8,388,608-element input limit as projects.

`InputLibrary` lives in the shared Inputs drawer for both visual and source projects. It starts collapsed, loads on open, previews all saved settings, and copies a selected configuration into the draft. It does not add a live fixture reference to the project. The composer then performs its existing shape checks, and a run captures the full copied specification. Invalid or unapplied input fields block saving to the library. Applying an input clears input-field errors while preserving unrelated constructor/code edits and validation errors.

`InputSpec.random_stream` defaults to `model` for backward compatibility. New UI random selections opt into `input`: a dedicated CPU `torch.Generator` seeded from `InputSpec.seed` generates the input independently of parameter initialization and does not consume the global RNG used by the forward pass. The worker retains the existing model seeding. Meta execution does not generate numeric values. The stream choice is part of fixtures, project signatures, custom-component checks, and run snapshots. Reproducibility is scoped to the current execution environment, shape, dtype, and seed; weights and PyTorch version are not pinned by a fixture.

Checks cover validation, persistence after restart, copy isolation, immutable run settings, large metadata-only saves, independent seeded inputs across different constructors, preserved legacy RNG behavior, and the unchanged forward RNG stream. Browser acceptance covers builder and custom-code loading, invalid-draft recovery, numeric/shape-only mode restoration, and narrow layouts.

## Uploaded tensor inputs

`POST /api/v1/input-fixtures/upload` streams an octet-stream body into a temporary file with a hard byte limit; name and original filename are bounded query fields. `input_files.py` checks the NumPy magic, format version, header length before reading the header, dtype, rank, element budget, and exact payload size before mapping data. Pickle is never enabled. Native-endian contiguous values are written under a fresh opaque ID in `.data/inputs/`; file metadata and the corresponding immutable fixture are committed together. Failed imports remove only their own temporary/partial files.

`InputSpec.uploaded` pins the asset ID, filename, canonical-file SHA-256, shape, dtype, and byte count. Its validator prevents mismatched dimensions, data types, or generator modes. API save/compose/check/run paths also require the exact stored asset metadata, preventing client-supplied paths or fabricated references. The worker receives the inputs directory separately from project JSON, checks metadata and checksum before user code runs, and makes a writable private array copy. Meta runs use `torch.empty` on the meta device. Individual custom-component checks use generated zero metadata at their actual incoming shape, while full-sequence checks retain the original uploaded input metadata.

`UploadInput` imports into the shared `InputLibrary` without replacing an in-progress draft. Applying remains an explicit action. Both editors display uploaded provenance and lock shape/dtype controls; switching to a generated source clears the file reference. Fixture copying clones nested asset metadata, and project signatures normalize absent references for older projects. Original logical values are retained; original Fortran strides and byte order are not portrayed as the imported tensor's memory layout. Large numeric inputs use the existing immutable paged snapshots after execution.

Tests cover all supported dtypes, Fortran and big-endian arrays, exact int64/non-finite readouts, paged values, meta execution, repeated in-place mutation, backend restart, reference tampering, corrupt/missing files, custom modules after shape changes, allocation/header bombs, partial/extra payloads, and rejected object arrays without unpickling. Browser acceptance checks import errors, successful application, fixed fields, source switching, recorded numeric values, and narrow layouts.

## Model composition

`Blueprint` stores the input-enabled flag and an ordered sequence of component IDs, kinds, and integer settings. `composer.py` owns the toolbox registry, bounded shape inference, validation, and Python generation. `/toolbox` exposes this catalog; `/compose` returns inferred stages and generated code. Project create/update canonicalizes code from a blueprint on the server. Invalid designs can be saved, but generate an explicit failure and are blocked from execution in the UI. Numerical mode checks model-weight and known intermediate sizes before constructing the model. Existing code projects have no blueprint and continue through the same runner.

`vision.py` supplies inspectable source for `TokenPreparation`, `ClassTokenReadout`, and `VisionTransformer`. The full ViT composes the existing patch embedding and pre-norm transformer block with these reusable sequence components. Shape inference counts one extra class token, learned class/position parameters, all block weights, final normalization, and classifier parameters. Fixed image resolution is validated at runtime; different batches are supported. This is an untrained educational model with logits output, no dropout, and no automatic positional interpolation. Tests compare the complete traced execution to an independent functional PyTorch reference, match modular assembly using identical weights, and exercise rectangular images and large shape-only batches.

`hierarchy.py` supplies reusable spatial embedding, window partition/restoration, window transformers, 2×2 patch merging, and spatial readout. `HierarchicalVisionTransformer` combines two fixed-window stages around one merge. Spatial stages use NCHW; partition packs row-major windows into `[B × windows_per_image, window², C]` for the shared `TransformerBlock`, and restoration reverses that layout. Patch grouping concatenates TL/BL/TR/BR neighbors into 4C features, then LayerNorm and a bias-free projection produce 2C. The full model validates both grids' window divisibility, supports variable batch sizes, and uses initialized parameters without shifted windows or relative-position bias. Pure shape helpers count parameters and bound scores by `B × windows_per_image × heads × window⁴`, along with expanded MLP intermediates, before numeric allocation.

`spatialGrouping.ts` recognizes a layout lesson only after validating the recorded module type, four connected operations, exact intermediate shapes, permutations, mapping rules, dtype, and successful non-mutating boundaries. It composes existing logical-index mappings in both directions; class names alone do not establish provenance. `SpatialGroupingView` displays all five recorded shapes, shares interactive tensor cards and 3D selection, and bounds neighborhood highlighting to 64 cells. It distinguishes value-preserving grouping from the later learned merge projection and reports recorded endpoint storage sharing separately. Tests compare every partition cell, inverse restoration, merge neighbor order, independent per-window functional attention, and the complete hierarchy against a separate PyTorch calculation. Large shape-only and non-contiguous cases remain bounded.

Tensor–tensor addition advertises the `broadcast_add` lesson only for compatible, non-empty shapes and finite numeric alpha. The frontend independently validates old/new traces, right-aligns axes, and computes both operand coordinates in O(rank), without an element-sized map. Reverse selection retains output coordinates on broadcast axes. `AdditionView` reuses tensor explorers and paged values; it never identifies arbitrary additions as residual/positional by shape alone. Captured outputs remain authoritative, and mutations keep the separate storage-change view. LayerNorm has its own group/affine lesson; GELU retains a semantic description with ordinary tensor inspection.

`Toolbox.tsx` defines the compact category toolbar and the on-demand searchable library panel. All tools shows category summaries instead of the full component list; selecting a category opens its components. `toolboxSearch.ts` matches normalized query words across the entire catalog, including custom class names and explicit aliases for supported components. Component definitions and parameter bounds come from the backend catalog. `App` controls which category is open; selecting a component closes that panel and opens its settings without changing the canvas scale. Project setup edits the name; input-node selection opens the shared Inputs drawer. The Custom category also exposes locally saved single-file PyTorch modules and their creation action. Generated source uses a read-only editor mode that permits selection, copying, and source navigation while hiding mutation controls; busy state is reserved for work in progress.

`BuilderCanvas` keeps design-time shapes separate from captured tensors: previews use `value_source=shape`, have no values, and are labeled inferred. Execution still produces an immutable run through the existing worker. Adding new components requires a registry entry, matching code/shape rule, and a numerical comparison against uninstrumented PyTorch.

## Custom component library

`CustomComponentDraft` validates syntax and constructor settings without executing code. SQLite stores immutable `CustomComponent` entries; toolbox responses include their metadata and source snapshots. A custom `ComponentSpec` pins that snapshot alongside optional per-node JSON arguments. Saving a new version changes only the selected instance.

`BuilderCanvas` retains constructor text by component identity rather than inside the selected editor. Valid JSON applies automatically to the instance; unfinished invalid text remains available after switching components or panels. Editing validity is separate from shape validity and blocks save/run until the text is corrected or reverted to the last applied arguments. Library defaults and recorded runs remain immutable.

`custom_components.py` owns explicit checks and namespace generation. Passive `/compose` requests only consult bounded in-memory check caches. `/compose/check` shares the execution lock with Run, executes custom modules on the meta device through the existing timeout-controlled worker, then checks the complete generated sequence to catch stride-sensitive failures. Any change to code, arguments, input configuration, recording mode, or sequence requires a matching check. Unsupported meta kernels and value-dependent behavior produce explicit errors. Results are not numeric tensor captures.

Generated code places each module's source in a separate namespace and aligns its compiled source line numbers with the displayed program. The recorder reads embedded source assignments to retain original variable names and source excerpts. Runtime guards also verify each custom output against its checked shape and dtype; differences fail the trace instead of silently using stale preview shapes. The initial sequence contract requires one non-empty rank 1–6 tensor in and out with a preserved dtype. Multi-input components in the sequence builder, per-component checkpoint remapping and multi-file reusable add-ons remain outside the builder contract. Dependency environments and multi-file entry points are available in custom-code projects. Model-level saved weights are supported for the complete generated composition. Custom-code projects support multiple forward inputs separately.

`CustomComponentDialog` provides source import, library metadata, and default JSON settings. The inspector's `ConstructorArguments` applies valid JSON automatically and retains unfinished invalid text until it is corrected or reverted. The existing generated-code, tensor, operation, and run-history views are reused. Generation performs the explicit custom shape check before saving and running; Preview custom shapes remains an optional builder action. Passive editing and composition previews never execute custom modules.

## Indexed volume renderer

`volume.ts` provides pure sampling, logical coordinate mapping, rotation, and cube-face projection. A large axis retains indices 0, 1, and its final index, plus a selected interior index if necessary. Gaps describe all omitted intervals exactly. The last three axes form spatial cells, the preceding axis forms separate volumes, and earlier axes are explicit fixed slices. Axes up to 16 expand fully within a total budget of 512 cells for thumbnails and 1,024 for enlarged views. If expansion would exceed that budget, only the largest necessary axes are condensed. Budgeting reserves room for a selected interior index, keeping compression stable during selection. Consecutive cells meet at their boundaries; only omitted intervals introduce geometric gaps. Isolating a slice frees budget for other axes. Paged numeric reads are split into concurrent requests of at most 256 indices, with a shared abort signal.

`TensorVolume` is reused for node thumbnails and the enlarged inspector. It projects the same unit-cell geometry for every layer; rotation changes the camera, not coordinates or values. Rear faces are culled and cells are painted in depth order. Cell text is clipped to its visible face. The volume is a compressed logical view, not a physical storage layout or a proportional image. `TensorVolumeDialog` adds per-axis navigation, gap drill-down, slice isolation, and exact-value readout. Numeric runs use the existing bounded snapshot endpoint; design and meta previews never invent numeric contents.

## Forward call configuration

`ProjectDraft` preserves the original `input` field and adds `input_name` (default `x`), `input_binding` (default positional), and up to seven `additional_inputs`. Each `ForwardInput` pins a name, positional/keyword binding, and full `InputSpec`. The computed `forward_inputs` property is the execution adapter; it is not a second serialized source of truth. Old projects and runs load without migration. Validation rejects duplicate/invalid names, positional arguments after keywords, per-input or aggregate numeric budget violations, and multi-input blueprints.

The API checks every uploaded reference on project create/update/run. Before executing source, the worker verifies and privately loads every numeric upload. It constructs the model with the legacy primary-input seed/dtype rules, binds placeholders against the actual bound `forward` signature, then builds every input with its own generator and dtype. Signature mismatch produces a named error before numeric generation. A single recorder captures all inputs as independent named roots with their own axis labels, and invokes `model(*args, **kwargs)` so module hooks still run. Keyword inputs participate in module boundaries and operation dependencies through the existing recorder. Shapes-only mode creates only meta tensors. Immutable project/run JSON includes the entire call configuration; changing an auxiliary input invalidates the displayed-run signature.

`ForwardInputs` owns collapsible input cards and the shared recording mode; `TensorInputFields` reuses the input library, upload provenance, and random-stream controls. Collapsed cards stay mounted so invalid unfinished fields cannot disappear from validation. The builder's `ComponentToolbar` displays icon categories horizontally with keyboard navigation; the left rail retains workspace navigation only. The component panel returns focus to its opening toolbar control on Escape.

Checks cover numeric cross-attention against PyTorch, keyword-only calls, mixed floating/integer inputs, module boundaries, partial failures, signature errors, independent RNG streams, old projects, saved histories, additional uploaded assets, and large shape-only inputs. Browser checks cover adding/removing inputs, invalid collapsed fields, a four-input run, toolbar navigation, and narrow layouts.

## Immutable model checkpoints

`SavedWeights` pins an opaque ID, display name, original filename, canonical-file SHA-256, byte count, timestamp, and bounded tensor manifest. `ProjectDraft.weights` defaults to null, preserving existing projects and seeded behavior. The `weights` SQLite table holds immutable library metadata; `.data/weights/<id>.pt` stores normalized CPU tensor values and standard state-dictionary version metadata. APIs list/import assets and explicitly check a draft's compatibility. Neither import nor selecting a checkpoint executes project code.

`weights.py` validates archive sizes/counts and the uncompressed PyTorch format, restricts deserialization with `weights_only=True`, checks metadata on the meta device before materializing values, and normalizes a fresh tensor-only state dictionary. Import uses a disposable worker with a 20-second deadline. There is no unrestricted loader fallback or custom allowlist. API project save/run/check paths require exact library metadata. The execution worker checks the canonical checksum before user source, constructs the model using the existing primary-input dtype/seed rule, compares exact keys/shapes/dtypes, and loads with strict matching. Weights attach to the complete model, including builder-generated module names. No remapping or partial loading is performed.

## Convolution neighborhoods

`operations/convolution.py` validates batched/unbatched Conv1D/Conv2D operands, matching floating dtypes, bias size, grouped channels, and exact output geometry before supplying the `convolution` interaction. Output channel determines its input group, and kernel channels remain local to that group. Browser arithmetic remains approximate and the immutable recorded output stays authoritative. ## Pooling neighborhoods

`operations/pooling.py` validates batched/unbatched floating-point 2D max, average, and adaptive-average pooling before supplying the `pooling` interaction. Positional and keyword arguments are captured by name. Geometry checks include output-size rounding and the ceil-mode correction that excludes windows starting beyond the input. Returned maximum indices must have the output shape and int64 dtype. All validated pooling outputs preserve input axis names unless an explicit source annotation overrides them. Unsupported or inconsistent traces retain general inspection.

`pooling.ts` independently proves the recorded geometry. Regular windows use stride, padding, and max-pooling dilation. Average-pooling regions stop at the declared padded extent: ceil overhang beyond it does not contribute to the divisor. The divisor is either the explicit nonzero override, the declared padded region area, or the real sample count. Adaptive bounds use exact integer floor/ceiling ratios with BigInt intermediates; non-divisible and enlarged outputs can overlap. Reverse selection solves regular stride/dilation geometry through shared `tensors/windowGeometry.ts`, also used by convolution, or computes adaptive output intervals directly. `PoolingView` links the existing 2D/3D tensor explorers and paged values. Average browser arithmetic is approximate; recorded outputs remain authoritative. PyTorch-generated fixtures are checked by both backend and frontend tests, alongside ceil/divisor, adaptive overlap, ties, non-finite, non-contiguous, and very large shape cases.

## Layer normalization groups

`operations/normalization.py` validates exact trailing normalized dimensions, matching floating dtypes and output shape, nonempty operands, finite nonnegative epsilon, and affine tensor shapes. Argument capture records explicit weight/bias tensor-or-null roles, so bias-only calls cannot be mistaken for scale-only calls. Semantic keyword ordering remains handled by the recorder. Explicitly unambiguous older traces are accepted; a two-operand trace with no affine-role evidence uses general inspection. The `layer_normalization` capability is independently validated by `layerNormalization.ts`.

Group and feature indices use logical row-major coordinates, independent of physical strides. A group contains the product of the trailing normalized dimensions; leading coordinates select the group, and trailing coordinates select its shared scale/bias entry. The frontend allocates at most 256 indices for complete group statistics, or eight for a selected window. No map proportional to tensor size is created. Statistics use a two-pass population-variance calculation with a shifted mean to retain small differences and exact constant groups. Epsilon is inside the square root; explanatory arithmetic remains approximate relative to PyTorch. Incomplete, missing, non-finite, or overflowing values never supply a fabricated finite result.

`LayerNormalizationView` loads on demand and shares the tensor explorer, 3D dialog, index controls, and paged snapshot hook. Its mean/variance/normalize/affine progression is explanatory UI, not synthetic trace nodes. Parameter selection preserves the current leading group; selecting either main tensor updates the paired coordinate and group. Shapes-only traces keep structural exploration. Larger numeric groups show full-group statistics alongside a bounded cell window and the recorded output. Tests independently compare population formulas, module/functional calls, reordered keywords, bias-only calls, multiple axes, non-contiguous inputs, constants/zero epsilon, non-finite values, and billion-element metadata. Shared PyTorch fixtures verify frontend reconstruction of every small-case output.

Large groups use `GET /api/v1/runs/{run_id}/operations/{operation_id}/normalization?group=…`. The endpoint validates the recorded LayerNorm operation and group bounds, then reads only the immutable input snapshot. `statistics.py` scans it twice in 16,384-element float64 chunks, respecting the existing 8,388,608-element numeric tensor limit. It validates snapshot shape, dtype, and logical contiguous layout; non-finite or overflowing groups return explicit statuses with null statistics. Missing/corrupt snapshots return a recoverable 410, while shapes-only traces return 409. The constant-size response contains group identity, count, mean, population variance, and denominator. No user code is executed and no trace nodes are added.

The frontend validates response identity and completeness, cancels stale requests, and keeps at most 32 immutable summaries in an LRU cache. Changing features within a group reuses statistics; changing groups, operations, or runs cannot display a previous selection's result. Values-hidden and shapes-only views do not request statistics. Endpoint tests cover multiple axes, logical order after transpose, later in-place mutations, persistence after restart, corrupted snapshots, low-precision input dtypes, chunk bounds, constants, non-finite inputs outside the visible window, and invalid requests. ## Variable names from source spans

The recorder reads the span of the instruction being evaluated from `co_positions()` and compares it with the value span of each `name = value` statement (`register_assignments`). An operation whose span equals the value is the variable; one inside the value keeps the name only if no later operation in the same frame completes that value. This replaces line-based naming and is correct for several statements on one line, multi-line values, and conditional values. Literal values are not registered, so an embedded component source string cannot claim the lines of its own code. Without column information the recorder falls back to the statement's first line.

## More cell rules

`relations.py` adds `prefix` (running totals), `pad` (constant borders), and `einsum` (validated letters and sizes) rules, exact `table` maps for `sort`/`topk` from their returned positions, and `replayed_selection`: for pure selections such as index tensors, Boolean masks, `flip`, or reflect padding, the recorder applies the same call to a tensor of positions while capture is paused and keeps the result as the map. Replay runs only in value mode for tensors of up to 4,096 elements and is discarded unless its shape matches the recorded output. Property getters (`x.T`, `x.mT`) are recorded under the property's name and share the layout adapter with `swapaxes` and `movedim`.

A replayed map is accepted only when its positions are whole numbers and every recorded output value equals the input value at its mapped position. This makes replay safe to offer for operations whose purity depends on arguments, such as `interpolate`: nearest-neighbor resizing passes and linear resizing is rejected. `dot`, `outer`, and `mv` reuse the einsum rule with a fixed equation. `one_hot` and `class_loss` (cross-entropy and NLL with class-index targets, no weights or smoothing) are validated by shape and dtype; the viewer recomputes each sample's −log p(target) from recorded scores for explanation only, and the recorded loss stays authoritative.

`mutation.ts` compares the before and after snapshots of an in-place write and reports the cells whose values differ. It is a difference of recorded values, not a write mask from PyTorch: a write that stores an equal value is not counted, and paged or shape-only snapshots are not compared.

`channel_affine` covers evaluation-mode batch normalization: the recorder notes which of the optional statistics and parameters were supplied, and the rule is offered only when training is off and both running statistics are present. `alignShapes` and `BroadcastAlignment` show operand shapes as broadcasting compares them; they add no rule and read only recorded shapes.

`diagnosis.ts` also explains failures that are not about shape: a `view` on non-contiguous memory, data-type mismatches, and out-of-range positions. These are recognized from PyTorch's message together with the recorded operand types and, for embedding indices, inline values. A suggested conversion names an operand and a call; none is applied automatically.

## Axis lineage

`tensors/axisLineage.ts` traces each axis of a recorded tensor back to the axes of inputs and parameters. A story is a list of terms (a source axis, or a numbered piece of one when a reshape split it) and an optional note. Reshape regroups axes only within runs whose element counts agree; consecutive pieces that rebuild a split axis rejoin. Permutes, reductions, projections, joins, einsum, and broadcasts each carry their own rule. An operation without an axis-level rule ends the story with a note such as "computed by conv2d" instead of guessing, and a tensor created without tensor inputs is its own source. `lineageOf(trace)` memoizes stories across one trace; `App` builds it once per run and passes it to `CodeEditor`, whose `TensorPeek` shows it, and `VariablesPanel` builds its own for shelf cards. `explainedLineage` hides stories that only restate the tensor's own axes. Inside the journey, `Walkthrough` provides the lookup through `LineageContext`, so every `TensorCard` in any lesson labels its axis badges with `shortAxis` origins (and `describeAxis` in the badge title) without threading props through each view; outside a journey the context is empty and badges are unchanged.

`scrambledAxes` reuses the reshape runs (`regroupRuns`) to judge a regroup only when every input axis in a run has a known story. A run cut into several new axes is scrambled unless its terms rejoin into one whole axis; a run merged into one axis is scrambled when all pieces of a split axis are present but not adjacent and in order. The `scrambled-axes` insight reports either case as a warning; `tensorInsights` builds the lineage lookup lazily, on the first reshape or product it examines.

Root terms carry their tensor's `role`. `unrelatedAxes` compares two axis stories only when every term starts at a model input, after rejoining split pieces; weights and tensors created inside the code are never judged, because they are shaped to match. The `unrelated-contraction` insight applies it to `dot_product` lessons (matmul, mm, bmm): the left operand's last axis against the right operand's second-to-last, and it suggests `transpose(-2, -1)` when the right operand's last axis is the one that matches.

`isBatchAxis` accepts an axis whose story is a single, unsplit, unnoted term from a model input whose axis name begins with `batch`. `batch-softmax` (a warning) uses it for the softmax axis; `batch-reduction` (a hint) for explicit reduction axes, only when the result keeps an axis larger than one.

The focused step view is laid out to fit its frame. `TransformationFocus` exposes a header slot (`FocusSlotContext`); `FocusSlot` portals a step's controls into it, or renders them in place when there is no slot (the compact inspector). ## Axis ink

`tensors/axisInk.ts` turns axis stories into colors. `inkOf(trace)` assigns the palette to the axes of `trace.input_ids` in order; a term from a model input takes its root's color, any other root takes `NEUTRAL_INK`, and a story without terms has no ink. A piece keeps its parent's color and reports `piece`; a merged story lists every source color. Tensor ids repeat across traces, so a lookup inks only the trace's own tensor object; `inkOfAll` tries the displayed run and the current shape check. `App` provides the lookup through `AxisInkContext` around the whole workbench. `InkShape` and `InkSize` render inked shapes for code inlays, canvas nodes, shelf cards, the input legend, and `TensorPeek`; `TensorCard` badges and `LayoutMorphView` titles use `inkStyle` and SVG `tspan` fills. The input legend is inked only while the draft's input shape matches the run's.

`tensors/inkShade.ts` makes animated cells speak the same language. `inkShade(ink, position, size)` ramps an axis's ink from 30% to 66% lightness along its positions (a merged axis walks through its sources' inks in order) and picks a readable label color. `storyAxis` chooses the default axis for a step: one whose story moves to another position, else one that is split, merged, or reduced, else the last inked axis, preferring larger axes. `LayoutMorphView` offers a **Color by** radio group (inked input axes plus memory order) and shades each mover by its source coordinate; `CanvasCellMotion` tints each flight with the same shade, applied as inline style so hover and focus outlines keep it. `TensorCard` grid axis labels and `TensorVolume` index ticks, block labels, and legend use the axis ink.

`TensorShape` renders any recorded tensor's shape in its ink; it is the one way views print a recorded shape outside `<option>` text, which cannot be styled. `inTrace` decides whether a tensor belongs to a trace: its own object, or a copy that matches id, name, shape, dtype, and storage, because lessons relabel axes with `{ ...tensor, axes }`. The ink and paint sources cover the displayed run, the current shape check, and a run opened for comparison. Lineage carries a `write` mutation's new state from the state it overwrote when their shapes match; `metadata` mutations, which can rearrange axes in place, are not carried.

`tensors/cellPaint.ts` paints cells by data origin. `sourcePosition` finds where a source axis (by default the first input's last axis with more than one position) sits inside a tensor's axis stories: a whole term reads one mixed-radix digit of a merged axis, and the pieces of a split axis recombine into the original index; sliced or padded axes, whose term sizes no longer multiply to the axis size, give no position. `cellPaintOf(trace)` shades that position in the source axis's ink, falls back to the tensor's own last single-source input axis, and paints only the trace's own tensor objects. `App` provides it through `CellPaintContext`. `TensorVolume` fills inked faces with `--cell-ink`, scaled by face lighting (`volumeInk.css`); `TensorCard` grids use the same paint for their squares (`gridInk.css`, which outranks the studio theme's translucent cell rules), brightening linked squares and quieting the rest. `LayoutTransitionView`, `ReductionView` contributors, `PatchEmbeddingView` grids, and `TensorPeek` use the same paint and fire (also in `gridInk.css`, whose button rules are specific enough to win over the lessons' own pressed styles); canvas flights carry the paint of the cube they leave. A selected cell uses the fire gradient: per-volume in 3D, and the shared `#tv-fire` paint server (a zero-size SVG in `App`) for 2D grids and motion cells.

Lineage reads a step's cell rule through `tensorRelation(..., { anyLesson: true })`, because dedicated lessons (activation, reduction) present steps that also carry a relation. Views still require the relation lesson before choosing the relation view.

## Elementwise activation lessons

`operations/activation.py` registers ReLU, GELU, sigmoid, and tanh as an `activation` capability. It checks exact input/output shapes and dtypes, nonempty geometry (including scalars), GELU approximation mode, and non-mutating arguments. ReLU also accepts real integer dtypes. The recorder preserves axis labels for these pointwise operations; mutation detection retains priority. Existing traces can use the lesson when the independently validated frontend geometry and arguments establish support.

`activation.ts` validates the captured operation, calculates bounded eight-index windows, and supplies explanatory function values and plot geometry. Sigmoid avoids exponential overflow; GELU uses the recorded tanh formula or a five-term erf approximation for its Gaussian CDF reference. Native float64 PyTorch fixtures validate both modes across zero and the tails. The plot line uses at most 242 samples independent of tensor size, retaining zero and the nonlinear neighborhood when the range expands; captured points use recorded outputs, including deviations from reference arithmetic. Plot coordinates scale values before subtracting, keeping opposite floating-point extremes finite. A fitted range scans only the eight visible pairs.

`ActivationView` loads on demand. Its 2D/3D explorers, flat-index navigation, keyboard-accessible plotted points, and captured-pairs table share one selected coordinate. Unsupported or non-finite numeric values never produce an invented point; shapes-only and values-hidden modes show a clearly labeled function reference without requesting values. The existing paged hook supplies the bounded input and output windows, cancellation, stale-response protection, and retries. Tests cover module, function, and method calls, GELU modes, scalar/non-contiguous/integer operands, mutation fallback, paged million-element runs, billion-element shape traces, numerical fixtures, chart bounds, and accessible structural rendering.

## Softmax score groups

`operations/softmax.py` validates a nonempty floating input/output pair with identical shape and dtype, an explicit positive or negative axis, and no output write. Scalars support axis 0/-1. Implicit dimensions and dtype conversions retain general inspection. The existing `normalization` interaction remains compatible with saved runs; `softmax.ts` independently verifies geometry before opening the dedicated lesson. Recognized window-score adjustment stages retain their existing mask/bias lesson.

The logical group index flattens all dimensions except the softmax axis. Within a group, members are separated by the logical stride of that axis, independent of original storage strides. Group/member ↔ flat-index conversion is constant-space. `SoftmaxView` shares selection between both 2D/3D explorers and the score table, retaining the cursor through Tensor details. The four explanatory stages show maximum, shifted score, exponential, and normalized reference weight without inventing extra recorded operations. Recorded weights and reference results remain separate. The table uses eight rows, full-value tooltips, and fixed 0–1 bars rather than rescaling a partial window.

Complete groups of up to 256 scores calculate in the browser. Larger groups use `GET /api/v1/runs/{run_id}/operations/{operation_id}/softmax?group=…`, which revalidates the saved operation and reads only its immutable input snapshot. `softmax_statistics.py` uses two scans in chunks of at most 16,384 logical positions: find the maximum and negative-infinity count, then sum shifted exponentials with `math.fsum`. Values stay within [0, 1], including zero for negative infinity and opposing finite extremes that underflow. NaN/positive infinity return `non_finite`; an entirely negative-infinity group returns `all_masked`. These statuses have null maximum/denominator rather than fabricated distributions. Missing/corrupt snapshots return 410; shapes-only runs return 409. No project code executes.

The response includes immutable run/operation/input identity, group, count, maximum, denominator, and masked count. The frontend validates identity, complete coverage, and numeric bounds, rejects stale/aborted responses, and retains at most 32 group summaries. Moving between scores in a group reuses its denominator; hidden values request no statistics. Shared native PyTorch fixtures and tests cover every axis, non-contiguous groups, float16/bfloat16/float32/float64 input precision, scalar outputs, masks, extreme values, full-group scans, later input mutation, restart persistence, metadata-only billion-element tensors, invalid requests, bounded caching, and cancellation.

## Mean and sum reduction groups

`operations/reduction.py` validates nonempty real tensor geometry, output dtype (including integer promotion and explicit casts), normalized axes, and `keepdim`. Empty dimension lists/tuples and `None` reduce all axes; scalar axis 0/-1 is handled without inventing a dimension. Duplicate axes, inconsistent output geometry, unsupported dtypes, and output mutations do not advertise the lesson. The recorder propagates surviving axis labels, unless source annotations explicitly provide them.

`reduction.ts` independently validates recorded runs and computes input ↔ output/term coordinates using logical axis order, including nonadjacent reduced axes and non-contiguous tensors. No element-sized mapping is allocated. A contributor window holds eight indices; full small groups contain at most 256. `ReductionView` loads on demand, pairs 2D/3D tensor selection, and shows kept/reduced axes, gather/add/divide stages, direct group/member navigation, and coordinate tables. Inspection mode preserves the lesson cursor.

Reference arithmetic requires the complete group. Floating references use compensated summation; mean scales contributions before summing to avoid unnecessary total-sum overflow. Small integer references use BigInt and retain decimal strings beyond JavaScript's safe range. Conversions other than exact widening to int64 omit reference arithmetic. Reference math does not reproduce PyTorch's dtype rounding, accumulation order, or integer wraparound; captured outputs remain authoritative. Tests verify native fixtures, exhaustive small-group membership, bidirectional mapping, dtype casts, mutation/empty fallbacks, paged million-element tensors, and billion-element metadata.

Groups larger than 256 cells use `GET /api/v1/runs/{run_id}/operations/{operation_id}/reduction?output_index=…`. The endpoint validates the immutable operation, output coordinate, geometry, and dtype before reading the saved input; it never executes project code. `reduction_statistics.py` generates at most 16,384 logical indices at once, fixing kept coordinates and traversing reduced axes in logical order. This supports nonadjacent axes, `keepdim`, and snapshots of non-contiguous views without a group-sized index map. Shared snapshot validation checks the numeric capture limit, shape, dtype, and contiguous saved layout. Missing/corrupt snapshots return a recoverable 410; shapes-only runs return 409.

Floating groups use two bounded scans with `math.fsum`: scaled contributions for the mean, then the unscaled total. A finite mean can remain available when the total overflows. Integer groups use exact Python integers in one scan, encoding totals outside JavaScript's safe range as decimal strings. Non-finite inputs and reference overflow return explicit statuses with null numeric fields. The constant-size response includes run, operation, input tensor, output index, count, sum, and result. `useReductionStatistics` validates identity and full coverage, cancels stale requests, and caches at most 32 summaries. Contributor-window changes reuse the selected group's summary; values-hidden and shapes-only views request none. Tests cover chunk bounds, multiple/nonadjacent axes, later mutation, persistence after restart, exact large integers, numeric edge cases, corrupt snapshots, cache isolation, cancellation, and retry.

## Unified project workflow

`NewProject` starts a project from code (pasted or uploaded statements, or a Python module class), a visual canvas, or a Git repository. `pythonProject.ts` keeps the bounded `.py` reader and editable module-class suggestion; creating a project never executes it.

`workflow/projectAction.ts` selects the single next action shown on the title bar's Run button and in the command palette. Missing names, inputs, or components and invalid code, input, or model settings turn Run into an actionable review step (Review code, Review inputs, Review model, Set up input, Add component); console projects are checked by their statements rather than the derived module. Builder readiness is accepted only for the current `compositionSignature`. A checking or stale result waits, while a custom-component check requirement still offers Run. On explicit runs, `prepareComposition` consults the backend check caches through `/compose` and calls `/compose/check` only when needed; an invalid result opens model review, and a valid result supplies the generated code. Review requests are counters: `ProjectEditor`, `ForwardInputs`, and `BuilderCanvas` reveal and focus the affected field (opening enclosing disclosures through `revealField`) when the counter changes.

A failed trace keeps its earlier steps and offers Fix code (Edit model for canvas projects) and Edit inputs. Fix code uses `runErrorTarget` to open the recorded file and select the failing line in `CodeEditor` (its `reveal` prop), but only while the file's current contents match the saved source.

The recorded `Walkthrough` keeps only the current operation or stage panel mounted while it is open, keyed by run and node identity. It stays mounted but hidden and inert while another panel covers it, preserving the selected cell, viewing axes, slices, lesson settings, and scroll. `InspectionActivityContext` pauses retained replays and closes any native 3D modal when the inspection becomes inactive, so a hidden portal cannot intercept input.

`FocusConnections` provides one optional navigation disclosure above input, operation, and stage lessons. `journeyConnections` groups actual visible graph edges by neighboring node, tensor, and operand/storage kind, preserving repeated operand positions and ordering destinations by recorded execution. It never scans later operations to guess consumers of a reused tensor ID. Collapsed targets use stage labels rather than claiming internal slots are module arguments; stage contraction preserves separate operand and storage links. The disclosure remains open across navigation within a run, renders six connections per direction per page, and labels model returns separately from unused results or failed steps. Following a connection restores keyboard focus to the new central lesson without stealing focus from an existing executed-code line.

`JourneyCanvas` keeps a separate pre-focus overview viewport (`viewport.ts`), which also tracks the scene layout and explicit selections. Returning from node inspection restores that pan/zoom, adjusted for drawer-driven size changes. Explicit Fit, canvas Home, and minimap actions replace the stored overview. Stage layout changes invalidate the old overview coordinates and fit the new graph; zero-sized hidden surfaces do not reframe it. The inspector's Code tab (Executed code) always reads the immutable run snapshot, while the editor and settings edit the current draft; the canvas heading marks a saved run that the draft has changed since.

`ForwardInputs` owns local input validity independently of `ProjectEditor`. Shape and value generation are visible first; advanced tensor options, saved/uploaded fixtures, argument binding, weights and environment setup use disclosures in Inputs & settings. The same input fields serve manual and code projects, eliminating separate builder shape parsing. Hidden panels retain validation state so closing a panel cannot accidentally enable an invalid run. Review inputs/code opens the affected card and enclosing disclosures, then focuses the invalid field. Source projects can still supply up to eight inputs; the visual builder retains its single-input contract.

Routine builder settings show a compact Connections summary; joins and explicit branches initially expose their source selectors. Each component retains its disclosure choice, while invalid source references and Review reveal the affected field. A completely empty builder omits its redundant validation/zoom dock. The recorded diagram keeps Previous/Play/Next and step selection visible in `SceneTransport`; Reveal steps and Restart live in its settings menu. Stage grouping actions (Group into stages, Show every operation) share the Stages menu, and the focused lesson owns the Executed code button instead of repeating it in playback. Tensor explorers expose large-axis paging and a single Go to cell disclosure directly; View contains only applicable axis/window settings.

Environment setup merges the selected environment into the latest draft so concurrent edits in Inputs are preserved. Request-version guards ignore completion after unmount, and a pending-request guard prevents duplicate setup actions; the environment-list response is also checked for cancellation before updating state.

## Code-declared projects and the library

`declarations.py` turns source code into a ready-to-run `ProjectDraft` without executing it. It parses the module with `ast` to find `nn.Module` subclasses and the chosen class's `forward` signature, then reads comments matching `# input`, `# model:`, `# constructor:`, and `# capture:`. A required forward parameter becomes a forward input: declared shapes, generators, dtypes, seeds, and bindings are applied, and anything undeclared gets the `[2, 4, 8]` default. Keyword-only parameters bind by keyword; parameters with defaults are skipped unless declared. Text declarations produce the same `text` generator input as the input editor. The docstring's first line is the default project name and the rest is the summary. A declaration that cannot be used becomes a note in `ReadProject.notes` and does not stop the read. Only missing modules or unparsable code raise `ValueError`, which `POST /api/v1/sources/read` returns as 422.

`library/` holds the numbered curriculum files (`NN_name.py`, each with a `# track:` comment). `library.entries()` reads them once through the same reader. `GET /api/v1/library` lists them. `POST /api/v1/library/install` creates every entry whose `NN · title` name is not already in the store. It saves in reverse order so that 01 is the most recently updated project, and calling it again adds nothing. Formatting excludes the library files (`[tool.ruff.format]`), so each `# axes:` label stays on its statement's line.

On the frontend, `NewProject` sends both **Library** selections and **Model class** code through `api.readSource`. Only an edited name overrides the docstring title. The resulting draft is created as it is; settings open only when there are notes, and the first note is shown as a notice. `App` installs the library when the workspace is empty, and the command palette's Restore library projects calls the same endpoint. `test_library.py` runs every entry in values and shapes mode, and checks that a read of a library file's code equals the installed project.

## Loop folding

`loops.py` records which loop iteration produced each operation. `file_loops` parses every user source file for `for`/`while` loops, keyed by the function that owns them: a code object's `co_firstlineno` (counting decorators), or 0 for module code. `LoopTracker` installs a `sys.settrace` hook only while the forward pass runs. It returns a line tracer just for frames of user files and counts each loop header's line events per frame. A header runs once before every iteration and once more when the loop ends, so the count is the iteration the body is in. A header event resets the counts of loops nested inside it, so inner loops restart on each outer pass. If another tracer such as a debugger or coverage is active, it keeps priority and operations carry no loop information. `Recorder.__torch_function__` walks the stack and calls `LoopTracker.context`, which records the enclosing loops of every user frame, outermost first, as `Operation.loops`. Operations evaluated on a `for` header, like the iterable, belong outside that loop unless the body shares the header's line. A `LoopStep.id` combines frame serials, header lines, and outer iterations, so every pass of an outer loop runs a distinct inner loop. Console runs shift loop lines with `scriptRun`, like source lines. Runs saved earlier have no `loops` and simply do not fold.

`journey/loops.ts` folds on the frontend. `loopFolds` keeps loops with two or more iterations whose operation signatures (kind, status, source file and line, result shapes) are identical, outer loops first; loops inside a hidden iteration go with it. `foldJourney` removes later iterations from the graph. Their edges are mapped to the first iteration, and edges that would run backwards (values carried into the next pass) are dropped, since the frame's return arc stands for them. Body nodes show the operation and tensors of the iteration chosen in `shown`, through `displayedOperation`, so selection, motion, lessons, and probes all read that iteration's records. `showStageIterations` does the same for collapsed stages, matching the call with the same module type and size. `playbackSteps` lists the first iteration, then one `loop:` step per fold, inner loops first. `Walkthrough` plays that list. A loop step runs its own clock (720 ms per repeat, at least 1.4 s) even when stepped by hand. `useLoopIteration` derives the iteration passing through from the clock and rerenders only when it changes. Before a loop the body shows iteration 1, during its step the moving iteration, and after it the last one, unless the pips (`chosen`) say otherwise. `locateOperation` maps an editor request for a later iteration to its first-iteration node. `JourneyCanvas` draws each fold as a frame around its visible members (padded for nested frames, at least 360 px wide). The frame has an HTML header with the loop text, iteration pips (a slider above ten iterations), and a return arc whose rise grows with the frame's width. The loop step frames the whole loop. Camera reframing compares layout signatures rather than graph identity, so swapping iterations never moves the view. `passLoops` lists recorded loops with several passes that are neither folded nor inside a folded loop's hidden passes. The canvas outlines each pass (`framePasses`). When the framed step is inside a loop frame, `sceneView` gets 64 px of headroom so the scene caption never covers the frame's header.

`stepping.ts` holds the debugger rules. `stepDepths` counts the stages around each playback step (a loop step takes its body's shallowest depth). `stepOverTarget` finds the next step no deeper than the current one, and `stepOutTarget` the next shallower step. `stopsAt` decides whether arriving at a step should pause for a set of step ids; a loop step stops for ids in its later passes. `Walkthrough` binds F10 (over), F11 (into), Shift+F11 (out) and Shift+F10 (back) on the window, replacing the app's earlier raw-operation F10 stepping. It ignores modified keys, prevented events and open dialogs, so the editor's Ctrl/Cmd+F10 (run to cursor, through `App.selectLine`) acts alone. It passes the targets to `SceneTransport`. `selectLine` cycles a line's steps when the current step is on it. Otherwise it picks the line's next execution after the current step, grouped by loop pass, at that execution's last step. `Walkthrough` reports its activation mark through `onActivated`. Once it is at least 0, `CodeEditor` marks the inlays of fresh lines whose steps all lie beyond it as `unlit`. `JourneyCanvas.lightOf` gives the nodes and the minimap the same light. `Walkthrough` passes the targets to `SceneTransport` (absent targets disable the buttons). `App` derives `warningSteps` from the run notes (warnings and errors with a node). With the remembered `pauseOnWarnings` option, playback pauses there as at breakpoints, and the pause records its reason for the transport's dot.

Breakpoints live in `App`, by project and file path, in `localStorage` (`tensorviewer.breakpoints`). `CodeEditor` toggles them from a margin left of the line numbers or with F9 at the caret. `App` turns every breakpoint line into the run's step ids (`breakpointSteps`, matching each operation's source file and line). `Walkthrough` checks the step it advances to during playback. An operation step, or a loop step whose later passes contain a breakpoint step, stops playback and records `pausedAt`, which `SceneTransport` marks with a red dot. Play clears it and continues.

`loopDrift` in `insights.ts` reads each recorded loop's passes, taking the last operation of each pass as the carried value. It reports a steady change of at least fourfold in the largest magnitude, up or down (within 2% per pass), as a warning located on the loop header and the last pass's operation; `locateOperation` then opens that pass. On the canvas, `[` and `]` change the shown iteration of the loop around the selection (or the only loop on screen). Inside a lesson, `Walkthrough` finds `passFold`, the innermost folded loop whose shown pass holds the current operation. `stepPass` changes that loop's chosen iteration and re-inspects the same drawn node with the lesson's last reported cell (`lessonCell`, reset per node). `passFold` anchors on the current operation, or on a stage's first operation, so `StageFocus` gets the same `pass` control for a collapsed call inside a folded loop. `TransformationFocus` renders the matching loop label with previous and next buttons, and the window key handler maps `[` and `]` to them while a lesson is open (not in form fields). `passRanges` gives each pass's last result range, which the canvas draws as the `PassStrip` beside the pips. `StageLoops` badges a collapsed stage that contains, but is not inside, a folded loop. `loopLines` gives the editor one chip per recorded loop header in the open file: passes, whether the loop is folded, and its first operation. `App` shows chips only while the file matches the recorded source. A chip asks `Walkthrough` for `loop:<id>` through the ordinary focus request, which it plays as the loop step, or for the first operation of a loop shown in full. `Walkthrough` reports the playing loop through `onCurrentLoop`, so the header line becomes the editor's active line. `CodeEditor` scrolls an active line outside the view into it, unless its text area has focus. `layoutJourney` places work that does not start from an input (`arange`, `ones`, a mask read from a buffer) just before its first consumer, so such chains stay inside the loop body that uses them.

## Light

`TensorVolume` takes `light`: `pending`, `receiving`, `active` or `lit`. It no longer chooses cell 0 by default: only an explicit `selected` cell burns, and never while pending. Pending glass loses its ink and almost all fill. Active glass ignites (`volume-ignite`) and keeps an ember drop-shadow. The canvas rules outrank the studio theme's `filter: none` on compact cubes. `Walkthrough` keeps a per-run high-water mark of the furthest operation index playback has activated and passes it to `JourneyCanvas` as `reachedThrough`. Activation is permanent: stepping back never lowers it, and only loading another run resets it. Before any step, only input roots glow. Steps beyond the mark are pending; the selected result (or every body node of a repeating loop) is active; everything else is lit, which on the canvas means a steady ember. `kindleAbove` is the mark captured when the current step began. Cube glyphs dominate canvas rendering, so `LitGlyph` passes a ref-backed, stable select handler to `StableGlyph`, a memo of `TensorGlyph` compared on tensor, selected cell, light, keyboard flag and highlight cells. The canvas's follow-up renders after a step (current operation, activation mark, loop reports up to `App`) then skip unchanged cubes, and a skipped render never keeps a stale handler. `LitGlyph` subscribes to the scene clock only for an active node that is kindling for the first time, reporting `receiving` until 72% of a playing step, so an already-glowing tensor never dims. It is keyed by tensor id so each loop pass ignites again. `TensorCard` burns its chosen cell only when `light` is `active` (the default for `tone="output"`; inspectors and stage focus pass it explicitly). Other cards mark the chosen cell as a source (`cell-source`): ringed and lit.
